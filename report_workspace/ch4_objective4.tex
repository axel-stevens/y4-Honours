\chapter{Objective 4: Synchronise Logging of Flight Telemetry and Radar Measurements}
\label{sec:obj4}

A single python 3 program on the \gls{sbc} handled both the flight controller and the \gls{sdr} in one loop. 
The code was split by device, a \texttt{Drone} class, which handled the flight controller interface, a \texttt{Radar} class, which handled the radar interface, and a small \texttt{main.py} script to run the overall program. Synchronising the radar captures and the telemetry is critical, as each radar capture needs a position and attitude before it can be georeferenced or used in later processing.

\section{Introduction}
\label{sec:obj4-intro}

To synchronise flight telemetry and radar measurements, a pilot-initiated control signal must be interpreted, processed, and transmitted through the entire drone integration system. This required the flight controller to be configured to output the signal, for the signal to be propagated from the transmitter to the radar, and for the subsequent radar capture to be synchronised with the drone telemetry. 

First a switch was activated manually on the transmitter, which was then propagated to the flight controller. The flight controller then output this signal over a drone communication protocol called MAVLink to the \gls{sbc}. The \gls{sbc} then triggered a capture request to the \gls{sdr} accordingly. The \gls{sdr} started the capture and transmitted the information back to the \gls{sbc}. This signal path is shown in Figure~\ref{fig:activation-signal-flow}. 

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.5\textwidth]{ch4-4_images/Activation signal diagram.drawio.png}
    \caption{Activation signal flow starting at the pilot transmitter and ending at the \gls{sdr}.}
    \label{fig:activation-signal-flow}
\end{figure}

This objective included researching and procuring a suitable \gls{sbc}, configuring the flight controller, designing software to interface with the flight controller and radar, implementing a post-processing script, and testing the built synchronisation system. The requirements of the system were the ability for a pilot to trigger the radar capture directly from a switch on the transmitter, and that every capture is associated with a telemetry log entry. The final system was a MAVLink-based Python program on board a Raspberry Pi 5 that interfaced with both the radar and the flight controller, synchronising the radar and drone telemetry.

\subsection{Flight Controller Configuration}
\label{sec:obj4-fc-config}

The flight controller needed to be configured to read in a signal from the transmitter and tie that signal to a specific channel. There were 8 physical switches on the transmitter. The switch that was deemed suitable was tied to RC channel 15 using the transmitter settings. The telemetry log only records \gls{gps} when the drone is armed. This setting did not suit the project, as the drone needed to be disarmed for the majority of the project. To enable \gls{gps} logging while disarmed, the \texttt{LOG\_DISARMED} parameter was changed in the config file to HIGH on the flight controller. Eventually the .tlog file was replaced by a .csv file on board the \gls{sbc} as it was able to read all relevant telemetry status' directly. 


\subsection{Final System}
\label{sec:obj4-final-system}



The benefit to the program being one system was the fact that all the timing was able to use a single clock, which was \texttt{runtime} (seconds elapsed since the start of the program). Both the telemetry log and the radar used this value, and shared the same time base which is what made synchronisation possible. 


\subsubsection{MAVLink Interface}

The \gls{sbc} interfaced with the drone via MAVLink, a communication protocol used to interface between flight controllers and desktop computers, which the Raspberry Pi 5 running Ubuntu resembles in architecture. The physical connection was over \gls{usb}, and the software interface was handled by the \texttt{pymavlink} python package.  The communication method was originally PWM with one of the servo channels on the flight controller, however this was replaced with MAVLink because MAVLink only required one wire to connect instead of two, and was not dependent on the safety switch of the drone (the first iteration is shown in Appendix~\ref{}). 

The program blocked until it received a \texttt{HEARTBEAT} signal from the flight controller which confirmed the link and gave the target system and component IDs to be used by later commands. Instead of relying on default stream rates, the program sent \texttt{MAV\_CMD\_SET\_MESSAGE\_INTERVAL} commands to request each message from the flight controller at a fixed rate. The message IDs of the key messages is shown in Table \ref{tab:mavlink_messages}.


\begin{table}[htbp]
    \centering
    \caption{MAVLink messages requested from the flight controller and their use.}
    \label{tab:mavlink_messages}
    \begin{tabular}{llcl}
        \toprule
        \textbf{Message} & \textbf{ID} & \textbf{Rate} & \textbf{Used for} \\
        \midrule
        \texttt{GPS\_RAW\_INT}         & 24  & 1\,Hz   & Fix type, satellites, latitude, longitude \\
        \texttt{GLOBAL\_POSITION\_INT} & 33  & 5\,Hz   & Altitude (AMSL and relative), groundspeed \\
        \texttt{ATTITUDE}              & 30  & 5\,Hz   & Roll, pitch, yaw \\
        \texttt{BATTERY\_STATUS}       & 147 & 1\,Hz   & Voltage, current, remaining capacity \\
        \texttt{VFR\_HUD}              & 74  & 2\,Hz   & Requested but not parsed \\
        \texttt{RC\_CHANNELS}          & 65  & 5\,Hz   & Channel 15 (radar trigger) \\
        \texttt{HEARTBEAT}             & 0   & Default & Armed state, flight mode \\
        \bottomrule
    \end{tabular}
\end{table}


On each loop in the \texttt{main.py} file, \texttt{update()} drained every queued message with a non-blocking \texttt{recv\_match(blocking=False)}, and so the program was never stalled by a slow link as the stored value was always the latest received. 


Raw MAVLink fields were converted to \gls{si} units upon reception, including converting latitude and longitude from degE7 to degrees, altitude from millimetres to metres, and voltage from millivolts to volts. 

The armed status and flight mode of the drone was decoded as part of the \texttt{HEARTBEAT} message sent from the flight controller. 

The radar was triggered from a switch on the pilot's transmitter which was mapped to channel 15. However, instead of reading in a PWM signal output from the flight controller, the signal was read through the \texttt{RC\_CHANNELS} MAVLink message (shown in Table~\ref{tab:mavlink_messages}).The trigger logic was rising edge detection, as the encoded data in the MAVLink message was pulse width. 



A capture was requested by the main script to the radar only when the pulse width was above 1800 $\mu s$. The capture logic was sticky; the switch had to be seen as low before a new capture could be requested (which was a pulse width below 1200 $\mu s$). The deadband was widened from the previous iteration as it was found via oscilloscope that a valid signal never goes above 1200 $\mu s$ or below 1800 $\mu s$. The sticky logic prevented one switch from firing repeatedly, ignored the noise in the invalid range, and prevented a switch left high at startup from requesting a capture. Both pulse width parameters can be changed easily in the config file. Buffering was not used; if the radar was still busy, the request was rejected and a message printed, instead of the request being queued. The reason for this was predictability; the timespan of the radar capture is too long for buffering to be feasible. 

On each script startup a telemetry log in the form of a .csv file was created from the program, named with the start date and time, so that a telemetry log never overwrote a previous log. Each row in the log held sixteen telemetry fields and five radar fields of data, in addition to the program runtime. Among the five radar fields was the file name of the radar capture (if one occurred), so that each radar capture could be matched directly to the telemetry rows. 

To view live data for verification and testing, a terminal dashboard (which was viewed over \gls{ssh}) showed flight state, \gls{gps}, attitude, battery voltage, the pulse width of the RC channel tied to the activation of the \gls{sdr}, and the radar status. The display was refreshed at one Hz; a parameter changeable in the config file. A screenshot of the display with demo values is shown in Figure \ref{ch4-4:display}.

\subsubsection{SDR Interface}

The \gls{sbc} and radar did not communicate directly. Instead, the capture executable file was run by the \texttt{Radar} class in the program as a subprocess. This was to ensure appropriate separation between the two systems in order to minimise complexity. Under this method, the \gls{sbc} was only responsible for scheduling and bookkeeping of the radar captures. 

The capture settings for the radar existed in a \gls{json} file which was read by the program at startup, so that parameters could change between flights without editing code. Among these settings were the executable and firmware paths, output folder for the radar captures, duration of capture, and sweep time. The radar capture cycle was modelled as a state machine, the diagram is shown in Figure~\ref{fig:radar_state_diagram}.

Each capture file was named according to its capture number and runtime on capture. Together with the per-row radar columns in the CSV file, this gave two independent ways to align the radar capture data with the telemetry data sets.


\subsection{Post-Processing}
\label{sec:obj4-post-processing}

A post-processing script that takes the \gls{sbc}'s synced .csv file and draws the flight path on an interactive map was created. The script is shown in Appendix \ref{app:obj4-telem-data-visualisation}. When a new radar capture starts, a marker is placed on the interactive flight map at the location. The script erases the first row of data, as the longitude and latitude start at invalid value 0. This is because the flight controller initially outputs default values before beginning data recording. Coordinates are already in decimal degrees from the \gls{sbc} program, so they are plotted directly. The script was run on a desktop \gls{pc}, not the \gls{sbc}. Data visualisation was done after capturing, so using a \gls{pc} was appropriate.  \gls{sdr} data was not processed in this stage. \section{Results and Discussion}
\label{sec:obj4-results}

To verify the control system, three tests were conducted, evaluating the key requirements of the system; \gls{gps}, radar capture response, and computational overhead. The GPS drift and radar tests were done using existing testing data; the five tests from the ground integration testing. This was due to it being infeasible to carry the drone out for another ground integration test solely for the purpose of obtaining benchmarks on one subsystem. The computational overhead test was conducted on a separate occasion, as it was possible to do so from indoors.

An average of how long it took for the radar to capture between activating the trigger and starting the capture was taken for all five logs from the ground integration test. Between the first four tests and the last one, the settling time of the radar before capture was changed, which affected the latency. As such in the results, the first four tests the mean latency is subtracted by 4 s to offset the settling time. The results are shown in Table~\ref{tab:ch4-capture_latency}.

The mean latency across all tests is approximately 2s. The low standard deviations of 0.24 ms and 0.41 ms within each configuration shows that the trigger path is stable. The program logged data at 1 Hz, so the switch could have flipped up to 1 second extra before the logged row, so the true latency is thus between approximately 2 and 3 seconds, and the numbers shown in Table~\ref{tab:ch4-capture_latency} is a lower bound. 

\subsection{Computational Overhead}

To address the tight computational requirements of the airborne system, a computational overhead test was conducted. Three seperate tests were run. The first test was recorded while the system was sitting idle and not running the program. The second test was recorded during program runtime and no radar captures were made. The third test was recorded during program runtime while continously capturing radar data. The first test provides a baseline for the system usage, the second a baseline for the program, and the third the behaviour of the system during operation. \section{Summary}
\label{sec:obj4-summary}

Objective 4 aimed at implementing the full control cycle for the airborne \gls{sdr} system. Where a switch from the transmitter propagates though the system and activates a radar capture. Objective 4 also aimed at synchronising the radar and telemetry data sets, allowing the radar capture to be georeferenced. A Raspberry Pi 5 was chosen due to the \gls{sdr} \gls{usb} 2.0 requirement and for room for future onboard processing. The interface was designed at three phases, and ultimately ended with a MAVLink connection over \gls{usb}. The MAVLink version of the program simplified the wiring and removed the safety switch dependency present in the previous two versions. Logging of telemetry and radar state was done by one Python 3 program and data was logged to one .csv file per program run. The activation logic was a latched trigger which runs a flush, settle, capture and cooldown sequence of radar capture. Capture locations of radar data were plotted on a separate \gls{pc} program on an HTML map for visualisation. The stationary \gls{gps} drift of the system had a standard deviation of 0.05 to 0.61 m and a worst case of 1.14 m from the mean. The trigger to capture latency averaged 2.007 seconds across 13 documented capture events, however due to the refresh cycle of the system the true capture latency is 2-3 seconds (which can be adjusted). The computational overhead of the program was negligible, the \gls{cpu} usage remained below 1\% and the \gls{ram} usage rose from 3.6\% to 3.85\%, which suggests feasibility for a smaller \gls{sbc} system. The limitations are the settle-delay setting error in the first four logs, and the reused ground data tests. Future work involves either downscaling the hardware or creating a more sophisticated program that allows the full use of the computational power.
